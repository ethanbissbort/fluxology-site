# Repo Audit — August 8, 2026

Second full audit, covering the repository as it now stands: the marketing
site, the three dashboard sub-sites, both backend services, the deployment
topology, and the new write-capable MCP connector.

Every finding here was produced by one agent and then independently
**re-tested by a second agent instructed to refute it**. Verifiers
regenerated evidence themselves rather than trusting the finder's, and judged
severity independently. Roughly half of all findings were downgraded in that
pass, and two were refuted outright — those are listed below, because knowing
what *isn't* wrong is part of the result.

## Scope and method

Six phases, 22 agents:

1. **Understanding** — 4 agents mapped the site, the dashboards, the backend,
   and the project's purpose and history from scratch.
2. **Bug hunt** — 4 agents across dashboard-api, the dashboard frontends, the
   main site, and infra/CI/edge.
3. **Feature oversight crawl** — 1 agent on promised-vs-delivered, unreachable
   code, sibling inconsistency, and operational gaps.
4. **Adversarial verification** — 5 agents re-testing all 80 findings.
5. **Web test suite** — 738 automated checks across 13 phases.
6. **Performance** — 1 agent, numbers-first, including what *not* to change.

Then the MCP connector arrived mid-audit and received the same treatment:
3 hunters (auth/write-path, protocol/architecture, validation/tests) and
3 adversarial verifiers.

**Result: 121 confirmed unique findings — 8 high, 35 medium, 68 low, 10 info.
2 refuted.**

## The pattern worth naming

The high-severity findings are not crashes. Every one of them is a case of
**the system reporting success while doing something else**:

- a dashboard badges an unknown price as the best deal on the board
- an import reports "Workspace imported" while destroying hand-entered notes
- the contact form's no-JS failure page reads "Inquiry received"
- the MCP connector reports `changedFields: []` while persisting the change
  that corrupts the dashboard
- write tools declare themselves non-destructive while able to retire a
  dashboard in one call

Nothing here breaks loudly. That is the defining risk of this codebase right
now, and it is why the dashboards — decision-support tools — carry more
severity than the marketing site.

## The test suite that proves the wrong thing

The MCP connector ships 163 passing tests. A verifier copied the service and
deleted the pipeline's **entire step-9 business-rule gate**: still 163/163.
Instrumented across the suite, step 8 (Ajv schema) rejects 8 records and step 9
(business rules) rejects **zero**. Individual rule mutations *are* killed — by
one direct unit test each.

So the suite proves the rules **exist**; it does not prove they are **wired
in**. Separately, `unit.test.mjs:324` asserts null-tolerance as correct, so
fixing finding #1/#6 is a test-breaking change: the suite currently encodes the
bug as the specification.

`dashboard-api` — the other service that writes persistent state — has no tests
at all, and nothing in CI runs the one suite that does exist (`contact-api`,
32/32 passing).

## No single source of truth for the feed schema

Five independent definitions: each dashboard's `data/schema.json`,
`dashboard-api`'s validation, the MCP connector's Ajv schemas, its category
rules, and each frontend's implicit expectations. They already disagree — a
numeric eBay `itemId` derives a valid id and then fails Ajv. This is the root
cause behind findings #1, #6 and #7.

## Infrastructure

- **The dashboards' unhashed `app.js`/`styles.css` are served
  `max-age=31536000, immutable`.** Reproduced through a counting proxy: after
  editing the served file, two reloads re-fetched the HTML and made **zero**
  requests for `app.js`. Every dashboard bug in this report is unfixable for a
  year for returning visitors. HTML is `no-store`, so you also get version
  skew. Fix by versioning the reference from the no-store HTML.
- **One commit dropped five capabilities.** `afa4ed9` deleted `caddy/Caddyfile`
  and replaced it with a markdown doc carrying only routing. Lost: the access
  log, HSTS, `header_down Location` rewrites, timeouts/header cap, and
  `health_uri` health checking. `docker/apache/httpd.conf` still cites the
  deleted file in four places, including load-bearing HSTS guidance.
  **HSTS is currently emitted by nobody.**
- **Nothing logs per-request**, so auth failures leave no trace: 2,000
  wrong-token attempts produced four log lines, none about auth.
- **The edge contract is 12 routing rules across 4 hostnames, outside this
  repo, untested.** When it breaks, dashboards fall back to stale build-time
  snapshots — and still print `Live · N listings`. A feed dated 2019 renders as
  "Live". The failure is green.
- `services/contact-api/data/inquiries.jsonl` — the local-dev path the README
  recommends — is **not git-ignored**. Real PII can be committed.
- Backups are documented three times; **restore zero times**. The documented
  restore primitive silently drops `hardAllInCeilingCad`, `appVersion` and
  `searchName`, and cannot restore `audit.jsonl` or `inquiries.jsonl` at all.

## Web test suite

738 checks, 674 pass, 64 fail. 26 initial failures were re-tested and proven
harness artifacts.

Notable new failures: `compressHTML` collapses the whitespace between a closing
inline tag and the next word to nothing, so the homepage renders **"…operate in
Ontario.The four operating names…"** and the contact-received noscript reads
**"your inquiry was notsaved"**. The hamburger is 40×31 px across 768–1150 px —
the entire range where it is the only navigation. The touch-target rule is
largely inert (`min-height` on `display:inline` links; form fields not in the
selector at all). Dashboard search boxes have zero focus indicator, and `#live`
is not a live region.

Clean: no horizontal overflow at any viewport; CLS 0.0000 on all five marketing
routes; Office Scout survived all 9 doctored feeds (Deals and Jobs poisoned
themselves); Jobs passes 23/23 on a synthetic feed — it is empty, not broken.

## Performance

Baseline: `dist` = 134 files / 6.89 MB (5.87 MB images, 328 kB fonts). HTML,
CSS, client JS and the service worker are all genuinely minified.

Two items are **regressions introduced by the August 2 audit**:

1. **The service worker primes every image on install.** First mobile visit to
   `/` is 87 requests / 4,768,282 B, versus 26 / 646,084 B with the SW blocked.
   Dropping image extensions from `HTML_ASSET_PATTERN` and using
   `cache:'default'` for `/_assets/` gives **44 requests / 889,544 B (−81%)**
   with offline render verified intact. Low effort.
2. **`no-store` on HTML nullifies `prefetchAll`.** Desktop detail pages fetch 4
   documents (262 kB) that can never be reused. Low effort.

Further: AVIF renditions −27.8% on the image corpus (~−790 kB mobile homepage,
+200 s cold build); font consolidation on four single-weight families plus
unused Rajdhani weights, 328 → 220 kB at 0.006% pixel diff; Office Scout
CLS 0.2081 fixed by one `min-height`.

**Measured and rejected** — do not spend effort here: `inlineStylesheets:
'always'` (+42 kB brotli), `minify: 'esbuild'` (+2.8 kB), `cssMinify:
'lightningcss'` (byte-identical), narrowing variable-font ranges (identical
file), and minifying the dashboards' hand-written JS (**482 bytes brotli** for
the loss of the only readable copy of that source).

## Refuted, and impact corrections worth keeping

- **Refuted:** "a feed over `MAX_LISTINGS_PER_WRITE` can never be repaired" —
  a pruned `PUT /api/feed` repairs it. The real limit is that an oversized feed
  cannot be restored *at full size*.
- **Refuted:** "no slow-request bound at any layer" — Node's defaults bound it
  (slowloris killed at 74.5 s with a 408), and Node's 16 KiB header cap is
  *tighter* than the Caddy cap that was removed.
- The MCP **batch bypass is not reachable by a steered model**: the SDK sends
  one message per POST, and MCP dropped JSON-RPC batching in 2025-06-18.
  Exploiting it needs a bespoke client that is already authorized to write.
- The **prompt-injection entry point is listing content, not `generatedAt`** —
  `dashboard-api` forces the server clock on both write routes. But an
  11,219-character hostile title round-tripped byte-identical with
  `truncated: false`, so the vector is real via a different door.
- **Concurrent-write data loss is not reachable as configured** —
  `container_name` prevents `--scale`, and there is no `deploy.replicas`.

## The MCP connector's auth core is sound

Independently re-tested: `alg=none` and HS/RS confusion blocked by `jose`;
`aud`/`iss`/`exp`/`nbf` enforced; no ingest token reached any log line or tool
response across multiple runs; scope binding is not caller-influenceable; no
URL, path or token parameter anywhere; an unreachable authorization server
fails **closed** with a 503. The gaps are at the edges — tokens without `exp`
are accepted, `OAUTH_ISSUER` may be plain HTTP with an unconstrained
`jwks_uri`, and `/readyz` is unauthenticated and blanket-proxied by the
documented Caddy block.

## Suggested order of work

1. `null` handling across the five schema definitions (findings #1, #6, #7) —
   one root cause, three high-severity symptoms, and it is corrupting the
   decisions these dashboards exist to support.
2. Cache-busting for the dashboards' unhashed assets — until this lands, no
   dashboard fix reaches a returning visitor.
3. The two service-worker/prefetch regressions — low effort, −81% first visit.
4. Truthful reporting: the no-JS failure page, the MCP change report, and
   `destructiveHint`.
5. Restore the five capabilities lost in `afa4ed9`, starting with the access
   log — right now an auth failure leaves no trace anywhere.
6. Wire the MCP business-rule gate into a test that fails when it is removed.
